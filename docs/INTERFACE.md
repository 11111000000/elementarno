# Интерфейс: что за продукт и как он должен выглядеть

Документ отвечает на три вопроса: насколько хорошо сегодняшнее расширение
для opencode делает свою работу; каким должен быть интерфейс, чтобы работа
стала продуктом, а не демонстрацией; и как довести её до Android, macOS,
Windows и веба, не размножив кодовую базу.

## 0. Итог в одном абзаце

Сегодня у проекта **сильное ядро и отсутствующий интерфейс**. Ядро честное:
оно не придумывает улики, отказывает от ответа при недостатке оснований,
показывает потолок уверенности и умеет фиксировать, чем убита каждая
версия. Но всё это живёт в CLI и в одноразовой HTML-выгрузке; человек,
который хочет «проанализировать фотографию», должен знать репозиторий,
форматы JSON и команды. Интерфейса нет — есть калькулятор. Построить его
имеет смысл на существующем API: **одно веб-приложение, две формы поставки
(хостинг для веба и мобильных, локальный движок для десктопа)**, и одна
интеракция, ради которой всё затевается, — **цикл опровержения**, где
человек атакует утверждение машины.

## 1. Что уже есть — честная оценка

### 1.1 Что умеет расширение для opencode

| | |
| --- | --- |
| Протокол в коде | Утверждение без ссылки не проходит; уверенность режется потолком правила; нарушение лестницы — ошибка; обвинение и вывод о характере — ошибка |
| Отрицание | Утверждение, идущее дальше вывода улики, обязано быть атаковано; опровергнутое — убирается |
| Измеримость | 184 теста, 14 кейсов бенчмарка, харнесс над скиллом с метриками нарушений протокола, refutation coverage и discriminator coverage |
| Честность источников | Ведомость из 31 источника с вердиктами; 11 несуществующих ссылок найдены и исправлены |
| Отказ | «Улик недостаточно» — корректный результат, а не сбой |

### 1.2 Чего в нём нет

1. **Интерфейса.** Ни одного экрана продукта. `board` собирает
   самодостаточную HTML-страницу — это выгрузка для архива, а не поверхность,
   в которой живут.
2. **Хранилища дел.** API (`server.py`) stateless: `/perceive`, `/analyze`,
   `/reason`, `/nextshot`, `/session`. Дело — это набор файлов, разбросанных
   по диску. Нельзя открыть дело, продолжить его, найти его, поделиться им.
3. **Интеракции.** Доска статична. Ответ человека на вопрос «что снять
   дальше» никуда не возвращается. Цикл опровержения невозможен.
4. **Потока событий.** Разбор кадра — 30–60 с. В интерфейсе это превращается
   в вечное колесо, а пользователь должен видеть, что происходит по фазам.
5. **Второй среды.** Тексты не поддержаны: ни графа для них, ни правил, ни
   слоя восприятия. `facts` есть в списке коллекций движка, но его нет ни в
   схеме, ни в одном правиле.
6. **Глубины.** 49 из 56 правил не имеют подтверждённого источника; все
   правила — черновики с потолком 0.5. В интерфейсе, который показывает
   ссылки, это обязано быть видно — иначе цитаты становятся украшением.
7. **Разрыва восприятия.** Харнесс меряет движковое восприятие (recall 0.5),
   а человек-агент находит больше. Разница измерена, но не устранена.

### 1.3 Оценка по главному критерию

Главный критерий продукта — **доверие к выводу**. По нему ядро сделано
хорошо: оно честно отказывает, показывает потолки, требует опровержения и
не даёт модели выдумывать улики. По критерию **доступности** — ноль: то,
что
сейчас умеет, доступно только тому, кто знает протокол.

Разрыв не в качестве ядра, а в расстоянии между ним и человеком. Интерфейс
— это расстояние.

## 2. Что на самом деле нужно построить

### 2.1 Продукт — не чат с фотографией

Почти все приложения с рассуждением показывают ответ. Этот проект не должен:
его substance — **леджер с видимым эпистемическим состоянием**. Экран
ответом не является; экраном является доказательная цепочка.

Отсюда правило подачи: **ни одно утверждение не показывается без трёх
вещей рядом** — ссылки на правило, его потолка уверенности и результата
попытки опровержения. Ответ без этого — маркетинг; ответ с этим — разбор.

### 2.2 Три поверхности

1. **Дело (главный экран).** Слева — артефакт (фотография с подсвеченными
   регионами или текст с подсвеченными фрагментами). По центру — леджер,
   утверждения сгруппированы по ступеням лестницы. Справа — версии: вес,
   kill-log, различающий вопрос.
2. **Граф доказательств.** Улика → правило → источник → утверждение →
   версия, нитями, как на пробковой доске. И — обязательно — **тупики**:
   отклонённые утверждения, убитые версии, следы, под которые не подошло ни
   одно правило. След с тупиками читается как рассуждение; чистая прямая
   линия читается как продажа.
3. **Приём.** Перетащить фото, вставить текст, выбрать из архива. Смена
   среды меняет слой восприятия, а не леджер.

### 2.3 Одна интеракция, ради которой всё затевается: цикл опровержения

Машина предлагает отрицание («в кадре **не** было открытых ёмкостей»),
человек отвечает — и леджер пересчитывается на глазах. Это единственная
интеракция, которой нет ни у одного аналога: обычно пользователь уточняет
факты, а здесь он **опровергает вывод**.

Она же делает продукт честным в бытовом смысле: если утверждение не
выдержало нажатия пользователя, оно уходит, а не прячется.

Технически это требует одного: чтобы леджер был **записываемым и
перепроверяемым**, а движок — чистой функцией от (сцена, правила, леджер) к
(леджер, отчёт, версии). Сейчас это почти так: `validate()` и
`score_hypotheses()` чистые, нужен только HTTP-слой над ними.

### 2.4 Чего интерфейс не должен делать

- **Прятать отказ.** «Улик недостаточно» с объяснением и следующим вопросом —
  самый надёжный экран продукта. Его надо сделать красивым, а не спрятать.
- **Смешивать уровни уверенности.** Утверждение из черновикового правила и
  из проверенного — разные сущности в интерфейсе, не одна карточка с разной
  цифрой.
- **Показывать стиль как достоверность.** Персона — рендерер, и это должно
  быть видно (уже помечено в `render.py`: повествование ≠ доказательство).
- **Обещать `solve`.** Режим контрфактических правок не реализован. В меню
  его быть не должно.
- **Прятать состояние источника.** Правило с неподтверждённым источником
  обязано выглядеть иначе, чем правило с проверенным, — иначе цитаты
  перестают быть доказательствами.

## 3. Универсальность: фотографии, тексты, что угодно ещё

### 3.1 Что в ядре уже мультимодально

Ядро не знает, что такое фотография:

- правило — это запрос к графу наблюдений, а не к картинке;
- `requires` у правила объявляет, какие поля графа обязаны присутствовать;
- пак — просто набор правил с полем `domain`; новый домен = новый файл
  `rules/<pack>.json`, без правок движка;
- леджер, валидатор, скоринг версий, рендер и nextshot работают поверх
  абстракции «наблюдение → улика → утверждение → версия».

Это уже заложено в конструкцию и работает.

### 3.2 Что мешает

1. **Словарь схемы — фотошный.** `surfaces`, `objects`, `regions`,
   `observations`, `light`. Для текста нужен другой набор: `passages`,
   `statements`, `entities`, `claims`.
2. **DSL без логических операций.** Набор предикатов
   (`all`, `any`, `not`, `present`, `count`, `absent`, `rule`, `dangling`,
   `mismatch`, `max`, `distinct`) выражает пространственные и счётные
   отношения. Для текста нужны `contradicts`, `precedes`, `entails`,
   `attributed_to`, `quantifies` — то есть работа с содержанием.
3. **Белый список коллекций.** `KNOWN_COLLECTIONS` в движке — значит, новый
   тип графа требует правки кода, а не только нового файла правил.
4. **Ноль текстовых правил.** Интерфейс может принимать текст завтра, но
   разбирать его будет нечем: корпуса нет.

### 3.3 Целевая архитектура

```
                 ┌─ адаптер восприятия: фото ─┐
артефакт ───────┼─ адаптер восприятия: текст ─┼→ граф наблюдений
                 └─ адаптер: документ/аудио ──┘        │
                                                        ▼
                                          ядро: правила → улики → леджер
                                                        │
                                                        ▼
                                      интерфейс (леджер, граф, версии)
```

Правила не знают, откуда пришли наблюдения: пак «дом» работает и на
фотографии кухни, и на тексте рецепта, если в тексте есть наблюдения того
же вида. Новое средство = новый адаптер + новый пак, движок не трогаем.

Механическое следствие: `KNOWN_COLLECTIONS` должен стать свойством *типа
графа*, а не константой движка. Тогда добавление текстовой среды = новый
тип графа, а не правка ядра.

### 3.4 Текст: что нужно на самом деле

Не «кнопка вставить текст», а три слоя:

1. **Граф текста.** `passages` (фрагменты), `statements` (извлечённые
   утверждения), `entities`, `observations` (свойства, отрицания, темпоральные
   метки).
2. **Расширение DSL.** Логические и временные отношения.
3. **Корпус правил.** Первые 10–20 правил: противоречие в документе,
   утверждение без опоры, ссылка на несуществующий факт, смена позиции между
   версиями текста, авторство и датировка.

Честная оценка: интерфейс мультимодален будет через неделю работы,
**глубина** для текста — через месяцы и с нуля. Показывать пользователю
текст с честным состоянием «правил для этого домена ещё нет» — правильнее,
чем притворяться.

## 4. Платформа: Android, macOS, Windows, web

### 4.1 Матрица решений

| Вариант | Android+iOS | macOS+Windows | web | Локальный движок | Код | Вердикт |
| --- | --- | --- | --- | --- | --- | --- |
| Только веб (PWA) | как браузер | как браузер | да | нет (нужен сервер) | 1 фронт | базовый, не целевой |
| Tauri v2 | да | да | да | да (sidecar) | 1 фронт + обёртка | **выбран** |
| Electron | нет | да | плохо | да | 1 фронт + 100 МБ | нет: нет мобильных |
| Flutter | отлично | хорошо | средне | нет/плохо | 1 код + 2 веб-стека | нет: два стека UI |
| Kotlin Multiplatform | отлично | хорошо | средне | нет | 1 код | дорого для этого этапа |
| SwiftUI + Compose | два стека | два стека | нет | нет | 2–3 кода | категорически нет |

### 4.2 Решение

**Одно веб-приложение, две формы поставки.**

- **Веб и мобильный** — hosted: приложение обращается к развёрнутому движку
  по HTTPS. Мгновенный доступ, ссылка-дело, установка на домашний экран,
  камера через `getUserMedia` (а это ровно то, что нужно для протокола
  «до/после»).
- **Десктоп** — Tauri-обёртка над тем же фронтендом, которая запускает
  Python-движок локально (`elementarno serve` на 127.0.0.1) как sidecar.
  Отсюда: файлы не покидают машину, протокол работает офлайн, каждая папка
  разбирается локально.

Движок остаётся на Python: переписывать 5 300 строк ради UI — это потеря
исследовательской работы ради потери различия.

### 4.3 Почему не другие варианты

- **Electron** — нет мобильных целей, 150 МБ ради обёртки.
- **Flutter** — фронтенд леджера это текст и граф: веб-технологии тут лучше,
  а Flutter заставил бы писать интерфейс дважды (Flutter Web и нативный).
- **Kotlin Multiplatform / Compose** — сильный вариант «когда-нибудь», но
  сейчас дорог: нужен свой UI-стек, свой рендер графа, своя система
  состояния, и всё это до того, как показано хоть одно дело.
- **Нативные отдельно** — две кодовые базы, расходящиеся по смыслу, —
  ровно то, чего протокол не допускает: утверждения должны совпадать побайтово
  на всех платформах.

### 4.4 Где живёт движок и что это значит для приватности

- Модельные вызовы уже идут в MiniMax по сети. Значит, «полностью
  локально» невозможно, пока восприятие и рассуждение делает внешняя модель.
  Честная формулировка для пользователя: **сцена и дело остаются на
  устройстве; текст и картинка уходят модели — и это нужно показать
  явно**.
- Локальная обработка (правила, валидация, версии) не требует сети вовсе.
  Это ценно: протокол можно прогонять офлайн, на уже сохранённых делах.
- Деплой: один контейнер с Python-движком и API. Он stateless по сутям,
  но хранит дела; нужен надёжный стор — SQLite достаточно.

### 4.5 Мобильный сценарий, который у нас уже есть в замысле

Протокол съёмки «до/после» (`docs/CAPTURE-PROTOCOL.md`) — это готовый
мобильный сценарий: снял, убрал, снял, получил измеримый результат по
отрицательным уликам. Это, вероятно, сильнейший мобильный сценарий
продукта, и он сегодня проверяется только на синтетике. Приложение — способ
его превратить в реальность.

## 5. Как это должно выглядеть

### 5.1 Главный визуаль: хребет лестницы

Вертикальная ось — ступени вывода (`scene → activity → presence → role →
action`). Утверждения висят на своей ступени, как булавки на доске. Ступень
без своих улик пуста — и это видно сразу: пустота сама говорит, где
вывод остановился.

Это лучше списка: список скрывает, что между «место» и «действие» может
пропасть целая ступень, а здесь пропасть видна геометрически.

### 5.2 Три карточки с разной плотностью

- **Улика** — плотная: правило, якоря, источник со знаком проверки,
  конфаунды, исключения, физическая проверка.
- **Утверждение** — средняя: текст, уверенность с потолком, оговорки,
  **результат отрицания**, что опровергло бы.
- **Версия** — лёгкая: вес, на чём стоит, kill-log, различающий вопрос.

### 5.3 Как показывать неуверенность, не пугая

Не «уверенность 45 %» крупным шрифтом, а **шкала до потолка**: видно и
вероятность, и то, что выше 0.5 правило не даст никогда, потому что
источник не проверен. Потолок — это не ограничение, а содержательная
информация: он показывает, что мешает.

### 5.4 Как показывать источник

Значок состояния у каждой ссылки: **проверен / не проверен / не существует**.
Сейчас 49 из 56 правил имеют неподтверждённый источник, и это состояние
видно только в ведомости. В интерфейсе оно обязано быть видно — иначе
продукт обещает доказательность, которой у половины правил нет.

Это неудобная правда, но она же и есть содержание продукта: показывать
себя в состоянии «я ещё не проверен» — сильнее, чем притворяться.

### 5.5 Мобильный сценарий

Камера → превью → «что дальше снять» → съёмка → пересчёт. Один вопрос на
экран: **«что снять, чтобы различить версии?»** — это и есть мобильная
логика приложения, а не «загрузите фото и получите отчёт».

## 6. Технический контур

### 6.1 API v2

Существующий API — шесть маршрутов без состояния. Нужно:

| Что | Зачем |
| --- | --- |
| `POST /cases`, `GET /cases`, `GET /cases/{id}` | дело как объект: артефакт, сцена, леджер, находки, журнал |
| `PATCH /cases/{id}/ledger` | записать отрицание или правку и **перепроверить** |
| `POST /cases/{id}/answer` | ответ на вопрос «что снять дальше» → пересчёт версий |
| `GET /cases/{id}/events` (SSE) | поток по фазам: инвентаризация → след-проход → улики → утверждения |
| `GET /cases/{id}/board` | существующая доска как живая страница, а не выгрузка |
| `POST /cases/{id}/recheck` | перепрогон правил по новому восприятию |

Ключевое: **перезапись леджера → `validate()` → новый отчёт и новые версии**.
Это ровно то, что нужно для цикла опровержения, и это чистая функция,
которая уже есть.

### 6.2 Что меняется в движке

- `KNOWN_COLLECTIONS` → свойство типа графа (нужно для текста).
- Валидатор и скоринг — без изменений, они уже чистые.
- Появляется **хранилище дел** (SQLite достаточно) и слой событий.
- Правила остаются теми же файлами. Новый домен = новый пак.

### 6.3 Фронтенд

Одно веб-приложение без фреймворка-тяжеловеса или с лёгким: леджер — это
текст, граф и SVG-нити, а не сложное состояние. React + лёгкий
граф-слой (или вообще без него, если связи рисуются вручную — как в нынешней
доске). Тема — общая с доской: пробка, бумага, булавки, нити. Доска уже
задаёт визуальный язык; интерфейс должен быть её продолжением, а не
конкурентом.

## 7. Дорожная карта

Каждый этап с гейтом, который можно проверить числом.

| Этап | Что | Гейт |
| --- | --- | --- |
| 0. Хранилище дел | SQLite + `/cases` + сохранение артефактов и журнала | дело открывается после перезапуска сервера |
| 1. Живой леджер в браузере | экран дела: артефакт, утверждения по ступеням, версии | 3 кейса открываются и читаются; 0 утверждений без ссылки |
| 2. Поток событий | SSE по фазам, отмена, возобновление | время до первого утверждения видно пользователю; обрыв не теряет фазы |
| 3. Цикл опровержения | ответ человека → перезапись леджера → пересчёт | опровергнутое утверждение исчезает из ответа; 0 нарушений протокола |
| 4. Приём: фото + текст | перетаскивание, вставка, выбор среды | текстовый кейс принимается и честно показывает «правил для этого домена нет» |
| 5. Tauri-обёртка | десктоп: macOS, Windows, Linux | движок работает локально; дело не покидает машину |
| 6. Android | камера, протокол «до/после», вопрос «что снять» | пара снята и посчитана: negative_detected, FP, consistency |
| 7. Текстовый корпус | расширение DSL + 10–20 правил | текстовый кейс даёт улики со ссылками и потолком |

## 8. Метрики качества интерфейса

| Метрика | Что показывает | Сейчас |
| --- | --- | --- |
| `protocol_violations` | нарушения в ответе агента | н/п для интерфейса, 0 в харнессе |
| `time_to_first_claim` | сколько ждать первого содержательного утверждения | н/п |
| `refutation_coverage` | доля утверждений, атакованных пользователем | н/п |
| `claim_survival` | доля утверждений, переживших атаку пользователя | н/п |
| `questions_answered` | доля предложенных вопросов, на которые ответили | н/п |
| `source_visibility` | доля показанных ссылок с видимым состоянием проверки | 0 (состояния нет в UI) |

## 9. Риски

| Риск | Что делать |
| --- | --- |
| **Интерфейс обещает доказательность, которой у половины правил нет** | Показывать состояние источника. Либо сначала закрыть источники, либо честно показывать, что половина правил — не проверенные мнения |
| **Текст без корпуса правил** — пустой продукт | Показывать честное «правил для домена нет»; не имитировать глубину |
| **Движок на Python внутри мобильной обёртки** | На Android — hosted-режим; локальный режим оставить для десктопа, где Python ставится один раз |
| **Пишется интерфейс, а не продукт** | Гейт этапа 1 — не «красиво», а «дело открывается и читается» |
| **Две платформы разъедутся** | Один фронтенд; движок один; правила одни. Расхождение видно тестом: набор утверждений должен совпадать побайтово |
| **Медленно** (30–60 с на кадр) | Поток событий обязателен; иначе первый экран будет крутить колесо |

## 10. Что делать на этой неделе

1. **Хранилище дел** (`tools/cases.py` + SQLite) и три маршрута API. Без
   этого интерфейсу нечего показывать.
2. **Живой экран дела в браузере**: сервер отдаёт страницу, страница тянет
   `/cases/{id}` и рисует леджер по ступеням. Без дизайна, без анимаций —
   чтобы проверить, что формат ответа вообще годится для отрисовки.
3. **Значок состояния источника** в интерфейсе и в `board.py` — это дешёво и
   сразу поднимает доверие к карточкам.
4. Проверить гипотезу «формат годится» на четырёх кейсах: `mold-wall`,
   `kitchen-table`, `clean-kitchen-dining` и один текстовый (который
   заведомо разберётся в пустоту — и это тоже надо увидеть в интерфейсе).
