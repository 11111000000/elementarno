# Петля качества

Идеальной модели не будет с первого раза. Значит, нужен не «правильный
промпт», а **операционный контур**, в котором каждое изменение измеримо, а
каждое ухудшение откатывается.

## 1. Что считаем качеством

Вектор $\mathbf{Q}$ из `docs/MATH.md` §9. Пороги — не пожелания:

| Метрика | Смысл | Порог | Как падает |
| --- | --- | --- | --- |
| Citation completeness | доля утверждений с разрешающимися ссылками | 1.00 | валидатор в коде |
| Grounding precision | доля утверждений, чьи якоря есть в графе | ≥ 0.90 | выборочная ручная проверка |
| Calibration (ECE) | соответствие уверенности реальной частоте | ≤ 0.15 | по размеченному набору |
| Hypothesis top-3 | доля случаев, где истина в тройке | ≥ 0.80 | бенчмарк |
| Refusal accuracy | доля верно выбранных отказов | ≥ 0.85 | бенчмарк |
| FP rate | доля ложных срабатываний правил | ≤ 0.02 | бенчмарк в «теневом» режиме |
| Обвинительных формулировок | доля ответов с выводами о вине | 0 | валидатор `accusatory_framing` |
| Разрывов лестницы | утверждений со ступенью выше опорной | 0 | валидатор связности |
| Стоимость анализа | секунд и токенов на сцену | ≤ 20 с, ≤ 2 вызова | профилирование |

Правило-«тигр»: одна метрика не может падать, пока растёт другая. Рост top-1
ценой калибровки — это регресс, даже если цифра выглядит лучше.

## 2. Цикл улучшения (недельный)

1. **Собрать промахи.** Прогон бенчмарка + разбор реальных случаев, где
   движок ошибся. Классификация ошибок: промах восприятия / промах правила /
   промах формулировки / промах калибровки / отказ там, где не следовало.
2. **Сформулировать гипотезу.** Одним предложением: что именно исправляем и
   почему это должно помочь. Пример: «след-проход не классифицирует светлый
   прямоугольник как dust_outline, потому что спрашивает про следы, а не про
   границы → нужен кроп-допрос».
3. **Внести минимальное изменение.** Одно правило ИЛИ одна правка промпта ИЛИ
   один новый первичный вопрос. Не всё сразу.
4. **Измерить $\Delta U$.** Прогон по всему бенчмарку: было/стало по всем
   метрикам. Плюс стоимость: время и токены.
5. **Принять или откатить.** Принимаем, если $\Delta U > 0$ и ни одна метрика
   не упала ниже порога. Иначе — откат (см. §5) и запись в `rules/CHANGELOG.md`
   с причиной.

Правило недели — **одно**. Много одновременно = невозможно понять, что помогло.

## 3. Разметка

Что размечаем вручную на каждом новом кейсе:

- **presence** правила: сработало или нет (нужен верный ответ, а не наш);
- **correct suspect / scenario** — для top-k и Brier;
- **confidence bin** — насколько уверен был движок в верном/неверном ответе
  (для ECE): 0.1 / 0.3 / 0.5 / 0.7 / 0.9.

Правила разметки:

- двойная разметка, расхождения — арбитр (эксперт или консенсус трёх);
- размечается **не результат движка**, а свойство сцены (иначе разметка
  заимствует наши ошибки);
- каждый кейс хранит файл разметки рядом с кейсом, версионируется в git;
- 20 % кейсов — «слепые» (никогда не показываются движку) для честной оценки.

## 4. Теневой режим

Новое правило сначала не публикуется:

1. прогоняется по всему бенчмарку **без** влияния на вывод;
2. считается FP: сколько раз сработало там, где разметка говорит «нет»;
3. правило публикуется, если FP = 0 на размеченных кейсах и оно добавляет
   хотя бы один верный TP.

Ложное срабатывание хуже пропуска: один выдуманный пылевой контур подрывает
доверие ко всем остальным уликам.

## 5. Версии и откат

- Изменился смысл правила → `version + 1` + строка в `rules/CHANGELOG.md`.
- Улика хранит `rule_version`, поэтому старый отчёт нельзя молча переиначить
  новым правилом.
- Регресс → откат версии (git revert), а не «подкруткой порога».
- Порог ($\tau$, $m$, $\kappa$) понижать нельзя ради красных цифр: это
  перенос ошибки из метрики в доверие пользователя.

## 6. Регрессия в CI

```
python3 -m unittest discover -s tests -t .     # 21 тест, контракт
python3 tools/run_eval.py                       # бенчмарки и метрики
nix flake check                                 # то же в изолированном окружении
```

Падение любого из трёх — блокирует merge. Метрики хранятся как артефакты
(`.json`), чтобы видеть тренд, а не только «зелёное/красное».

## 7. Дашборд

Прогресс по метрикам и по backlog'у правил — через `paseo-progress`; один
экран: $\mathbf{Q}$ по неделям, backlog правил с ожидаемым $\Delta U$, список
кейсов, где движок отказался или ошибся.

## 8. Что не делаем

- Не чиним симптом промптом: если промах в восприятии, правка должна быть в
  восприятии (другой вопрос, кроп-допрос, другой проход).
- Не добавляем правило без источника — даже «на всякий случай».
- Не публикуем версию, если не измерили $\Delta U$.
- Не снижаем пороги, чтобы бенчмарк позеленел.
- Не считаем «умной формулировкой» замену измерению.

## 9. Артефакты прогона

Каждый анализ оставляет след, иначе аудит невозможен:

```
artifacts/<дата>/<кейс>/
  raw.json          сырые ответы модели (все вызовы)
  scene.json        нормализованный сцена-граф
  findings.json     сработавшие правила с якорями и источниками
  ledger.json       утверждения и гипотезы
  report.txt        финальный текст (любая персона)
```

Сырой ответ модели — часть цепочки доказательств: без него нельзя понять,
почему система пришла к выводу, и нельзя воспроизвести случай.
