# AGENTS.md — правила работы в репозитории ЭЛЕМЕНТАРНО

## Предметная область

Приложение делает **абдуктивные выводы по изображениям**: восстанавливает, что
происходило в сцене, по косвенным признакам. Любое изменение обязано
соответствовать протоколу доказательности (`docs/PROTOCOL.md`).

## Жёсткие инварианты

1. **Утверждение без ссылки на `finding_id` недопустимо.** Валидатор
   (`tools/elementarno/ledger.py`) должен отклонять такое утверждение. Не
   ослаблять проверки «чтобы проходили тесты» — чинить тесты.
2. **`confidence` утверждения ≤ `confidence_ceiling` правил-оснований.**
   Правило с `review_status: "draft"` не может обосновать утверждение с
   `confidence > 0.5`.
3. **Новое правило обязано содержать:** `id`, `version`, `title`, `domain`,
   `predicate`, `inference`, `confounds` (пустой список недопустим),
   `exceptions`, `falsification`, `sources` (непустой), `review_status`.
   Правило без источника — не улика, а мнение.
4. **Границы вывода о людях.** Допустимы только три уровня: присутствие
   (`step: presence`), действие (`step: action`), роль или привычка. Вина,
   намерение и черты характера из фотографии не выводятся. Обвинительные
   формулировки (виновен, убийца, преступник) отклоняются валидатором
   (`accusatory_framing`), формулировки о свойствах личности —
   (`personality_inference`). Не обходить эти проверки переименованием.
5. **Лестница вывода.** `scene → activity → presence → action`. Ступень
   появляется в ответе только вместе со своими уликами; перепрыгивать
   ступени нельзя.
6. **Отказ отвечать — корректное поведение.** Не ослаблять порог `verify`
   ради увеличения числа «ответов».
7. **Сцены и оценки о физике/пожаре/воде — только со ссылкой на источник.**
   Домыслы оставлять в `confounds` и `exceptions`.

## Стиль

- Документация, README, `docs/**` — **русский** язык.
- Идентификаторы, ключи JSON, имена файлов, коммиты, код — **английский**.
- Коммиты: Conventional Commits, английский, императив, тема ≤ 72 символов.
- Python: 3.11+, только стандартная библиотека (зависимость — отдельное
  решение с обоснованием).
- Без комментариев в коде, кроме случаев, где неочевидно *почему* решение
  именно такое (и тогда одной строкой).

## 8. Рекурсивное улучшение

Работа ведётся витками, а не задачами:

1. Прогнать харнесс (или живой кейс) и зафиксировать цифры.
2. Найти промах и классифицировать его: восприятие / правило / формулировка /
   истина / нарушение протокола.
3. Сделать **одно** изменение.
4. Перемерить. ΔU > 0 и ни одна метрика не упала — принять, иначе откатить.
5. Записать: строка в `CHANGELOG.md`, строка в таблице витков
   (`docs/PLAN.md` §2.1), при необходимости — новый кейс в бенчмарк.

Правило «одно изменение за виток» нарушать нельзя: без него непонятно,
что именно дало эффект.

## Процесс

- Ветка `feat/*`, `fix/*`, `docs/*`. Прямые коммиты в `main` — только
  первичный каркас.
- Коммит за коммитом, каждый самодостаточен и проходит тесты:
  `python3 -m unittest discover -s tests -t .` и `python3 tools/run_eval.py`.
- Правила версионируются: изменение смысла правила → бамп `version` и запись
  в `rules/CHANGELOG.md`.
